# GameBoy：显示缩放与性能分析

BDA 标题改为 `GameBoy`，普通包为 `dist/H1GBA.bda`，性能分析包为 `dist/H1GBA-profile.bda`。保留现有图标和 GB／GBC／GBA 支持。

## v0.12.3 MXU 并行插值与 v0.12.2 真机结果

用户真机 v0.12.2 日志的 TCU 校验/采样故障均为 0。两个普通比例缩放段分别约 59.200/59.736 逻辑 FPS，缩放写屏约 11.642/11.592 ms/画面；线性段 1518 个逻辑帧、758 个输出画面，29.582 秒，约 **51.315 FPS**，缩放写屏 **22.188574 ms/画面**，占运行时间 56.885%。RTC 粗统计 1517 帧/30 秒约 50.567 FPS，端点误差范围 48.935～52.310；与细分结果范围相容。平滑段累计 29 次音频欠载，失败/丢弃/显示错误为 0，正常退出。最长核心帧 138.732 ms，ROM I/O 平均 0.578 ms/逻辑帧，不能将所有长帧归因于缩放。

这次真机记录确认了平滑路径预算不足；v0.12.2 的指令量改善不足以保证真机达到目标速率。原日志只读归档 `build/real-h1/2026-10-05/h1gba-v0122-original.log`，SHA-256 `f40d4bc6762bc17d713ac2ce09ed5696656fffde699e2aa0847ae164fc6557b8`；报告 `v0122-profile.json`、`v0122-rtc.json`。F 盘原文件未修改。

v0.12.3 采用 MXU1 Q8MUL/Q8MAC 同时计算 RGB 通道乘积，Q16SLR 和 S32SFL 完成精确取整与打包；水平缓存改回每像素 4 字节 RGB888，两个缓存合计由 7680 降至 3840 字节，增加相同端点区间的直接填色，保留整行纯色快速处理。新汇编 `src/platform/linear_mxu.S` 按四像素展开，只处理 cached RAM 行。函数保存所用 XR1～XR6 和控制寄存器；计算这一小行时保存/暂时关闭 IRQ，恢复全部状态后才在外部复制到未缓存 framebuffer。无 GUI、音频或文件调用处于该临界区，IRQ 不跨整帧保持关闭。

启动时、PCM 开始前，对所有 1～255 权重与黑白/互补/随机通道做逐像素自检；日志记录 `LINEAR_BACKEND name=MXU1_Q8 selftest=1 irq_scope=cached_row state=preserved`。结果不匹配则使用标量路径，计时标记 `scaler=linear_MXU1_Q8_split4`。权重 0 与图像边缘使用直接行复制，避免将 256 放入 8 位向量权重。

对 v0.12.2 实际普通 BDA 的同帧比较，复杂 GBA 画面缩放指令量由 4,462,328 降至 3,478,011（**再减少 22.06%**），GB/GBC 由 3,095,720 降至 2,318,037（**再减少 25.12%**）。12 组帧全部逐字节一致，三个旧显示模式一致；这包括 MIPS 与 MXU 指令，乘法统计分别列标量和向量指令，不能据此推导真机 FPS。Unicorn 使用独立的 MXU 子集模型，单独核对所有权重、1/2/3/4/63/302/408 像素长度、尾部保护、源不变、IRQ 初始开/关与完整 MXU 状态恢复，检查 56,394 个像素；完整固件验证使用 QEMU 自己的独立 MXU 解码器。证据 `build/profile-unit/linear-v123.json`、`linear-mxu-v123.json`、`pause-v123.json`。

诊断包在完整 H1 V1.41 私有固件中实际通过 MXU 全权重自检，绿宝石平滑画面、长暂停/继续、TCU 还原和退出通过；1026 个输出画面 errors=0，音频欠载/丢弃/失败为 0，实际 AIC 录音 8.024 秒，NAND 导出 torn record=0。证据 `build/h1-emulator-test/evidence/v123-tcu-native.json`、`v123-native.log`、`v123-profile.json` 与截图/录音。QEMU 平滑写屏约 1.827 ms/画面，高于上一轮 1.067 ms；MXU 在模拟器中展开成软件向量运算，该变化是虚拟环境结果，不代表真实 MXU 流水线耗时。新版本实际是否达到 60 FPS，需要新的真机诊断日志确认。

指令编码依据 [Ingenic MXU 编程手册](https://www.setphaserstostun.org/ci20/X1000_M200_XBurst_ISA_MXU_PM.pdf) 与本机 QEMU MXU1 解码源码；未使用 MXU2 或高版本 MIPS 指令。

## v0.12.2 线性平滑加速

保持旧版的两方向 RGB888 双线性插值、8 位小数权重和两级取整，画面比例、边缘、颜色与平滑程度不变。横向按源像素区间处理，相邻目标像素共享端点、差值和固定项；只转换一次源像素，不再在平滑热循环查询 256 KiB RGB565 表。水平缓存分别存红蓝与绿色，纵向免重复拆分通道，插值改成两次乘法并按四像素展开。整行纯色时只算一次纵向插值；颜色不同的纯色上下行仍正确混合。计算与连续写屏之间保留 RAM 行缓冲，不读取 framebuffer，也不增加整帧缓存。额外静态 RAM 约 4.7 KiB。

实际普通 BDA 与归档 v0.12.1 在同一 Unicorn MIPS32 环境调用缩放函数，排除首次坐标/颜色表初始化和清边。GBA 240×160 复杂彩色/随机帧指令量从 5,583,512 降到 4,462,328（减少 **20.08%**），GB/GBC 160×144 从 3,830,184 降到 3,095,720（减少 **19.18%**）；整帧纯色或不同颜色的水平条纹减少约 72%，纯色背景中有局部彩色区域的测试帧减少约 53%。这些百分比是缩放指令量，不能当作游戏 FPS 或真机耗时提升。

12 组 GBA/GB 尺寸与纯色、棋盘、彩色、随机、水平条纹、局部图案均与旧 BDA 整屏逐字节一致；原三个显示模式也逐字节一致。独立像素参考再覆盖纯色行与复杂行之间的过渡、padding pitch、换尺寸、第二帧内容替换和黑边保留。测试脚本 `tools/benchmark_scaler_mips.py`，完整结果 `build/profile-unit/linear-v122.json`；平台与三个核心的暂停菜单/即时状态/设置恢复回归通过，`build/profile-unit/pause-v122.json`。

普通与诊断包均为 v0.12.2，保留 GUI+0x9D8 组合输入、PCM 音频、RTC 和延迟心跳。真机仍可使用诊断包，暂停/退出后将计时批量写到 `A:\GBA\h1gba.log`，`PROFILE_BUILD` 的缩放标记为 `linear_intervals_split4`。实际卡顿改善需要新平滑模式日志确认。

本次诊断包完整 H1 固件测试：线性段 1151 个逻辑帧/575 个输出画面，TCU 故障 0，缩放写屏均值约 1.067 ms/画面；该值来自 QEMU 的虚拟内存环境。全程应用音频 underruns/failures/dropped=0，1033 个输出画面 errors=0，正常退出。暂停核心冻结、TCU 原状态恢复/重新借用均通过；实际 AIC PCM 录音 8.012 秒。证据 `build/h1-emulator-test/evidence/v122-tcu-native.json`、`v122-native.log`、`v122-profile.json` 与截图/录音。历史平滑段 1.86～1.89 ms 来自另一场景时段，不作为严格配对提速结论。

## v0.12 保持比例线性平滑

普通包与性能包都增加第四种显示模式 **保持比例（线性平滑）**，现有 0 原始大小 / 1 保持比例 / 2 全屏拉伸的编号、默认值和行为不变，新模式编号 3。显示菜单逐次切换与 V 键都遍历四种模式，.cfg 的原结构和 CRC/A-B 保存不变，新版允许 scale=3 并按游戏记忆选择。普通包同时包含已获真机数据支持的 RGB32 RAM 行缓存；旧普通 v0.11 包在 build/v11-preserved-release 归档。

线性模式保持 GBA 408×272、GB/GBC 302×272 的比例与居中边框；按像素中心映射，边缘钳制到最后有效源像素，不和图像外的黑边混色。横、纵两方向均使用 8 位小数权重的整数 RGB888 插值，没有运行时浮点计算。预计算 X/Y 坐标与权重；两个水平过滤行轮换缓存，相邻目标行复用水平结果，纵向结果仍从 RAM 连续写到 framebuffer。原快速保持比例模式继续使用一个 RAM 行缓存，不增加双线性处理。

独立的四角加权参考检查 GBA/GB 尺寸、padding pitch、棋盘黑白/彩色变化图的所有输出像素；分离插值产生的两级取整与一次加权参考各通道差不超过 1。核对边缘钳制、黑边、第二帧替换为纯绿色、clear=0 外围标记保留，原三模式逐像素回归仍通过。菜单字库补上新文字，标签适配原显示按钮宽度。

同时完成上一份日志定位出的心跳干扰修正：普通/诊断包都先在 RAM 保留最后 8 条定期心跳及省略数，PCM 停止后暂停/退出提交，标记 deferred=1；关键硬件阶段日志仍即时关闭，日志句柄不跨游戏循环保持打开。平滑模式的真实耗时需要后续真机日志，不能沿用原快速模式的 11.64 ms/画面作为平滑模式测量。

完整 H1 V1.41 私有固件模拟器已验证诊断包的菜单选择、线性画面、两次继续、暂停帧数冻结及退出；TCU5 在暂停/退出精确还原，计时与 profiler fault 均为 0。首次长运行跨过心跳周期，日志仅在暂停停止 PCM 后出现 `FRAME_HEARTBEAT ... deferred=1`，正常 `APP_END result=0`，私有 NAND 导出 torn record 为 0。证据为 `build/h1-emulator-test/evidence/v12-tcu-native-recovery.json`、`v12-native.log`、`v12-profile.json` 和设置/游戏截图。首次脚本在返回根菜单后误发两次上键，重新打开显示页，随后修正脚本并在同一运行恢复测试；未将失败的首次脚本标为通过。QEMU 平滑段测得约 1.86～1.89 ms/画面，只用于验证运行路径，不代表真机总线耗时。

## 2026-10-05 第七份真机日志与 v0.11.7

新增 `PROFILE_TCU`/`PROFILE_TCU_REG` 和 `PROFILE_CLOCK_PROBE`，记录启用、门控、中断掩码、比较值、计数、控制寄存器、RTC 起止值、计数差、固件 tick、迭代数及退出原因。日志写入放在两次 RTC 参考边界之外，避免文件写入缩短校验秒。一次校验失败后，在同一启动中继续游戏不重复耗时校验。每段另记 `PROFILE_SETTINGS`，明确显示、跳帧和声音配置。

即使细分计时失败，`PROFILE_RTC_RUN` 仍记录第一/最后完成帧的 RTC 秒值、逻辑/显示帧数，排除加载和菜单。它只有 1 秒分辨率，长样本可给出近似帧率范围，不能提供 CPU/渲染/音频耗时占比。可单独运行 `python tools/analyze_profile.py h1gba.log --environment real-h1 --coarse-only`。该诊断版本仍须真机确认，不把 QEMU 成功当作真机成功。

第二份原日志只读保存为 `build/real-h1/2026-10-05/h1gba-v0111-original.log`，结论为 `v0111-log-analysis.json`。原用户文件未修改。

v0.11.2 当前包完成 QEMU 固件检查：观测频率 32766 Hz，暂停前 884 帧/3 窗口、恢复后 660 帧/3 窗口，均 `fault=0`；两段 RTC 粗统计有效，长暂停后继续及退出时的状态还原通过。证据为 `build/h1-emulator-test/evidence/v112-tcu-native.json`、`v112-tcu-emerald.log/json`、`v112-rtc-emerald.json`。本次第三份真机日志已确认该版校验失败，详见上节。

原 v0.11 性能包在真机的 `PROFILE_CLOCK` 为 `hz=0 ready=0`，所有窗口为空，不能得出耗时占比或精确 FPS。JZ4740/JZRISC 没有 CP0 Count，而 QEMU 使用的通用 MIPS CPU 提供了它。Linux 的 [Ingenic CPU 检测代码](https://raw.githubusercontent.com/torvalds/linux/v2.6.37/arch/mips/kernel/cpu-probe.c)明确关闭该计数器支持；[JZ4740 时间实现](https://raw.githubusercontent.com/torvalds/linux/v2.6.37/arch/mips/jz4740/time.c)使用 TCU。旧日志中的 `RTC_stopped` 是失败校准的误导性原因，游戏 RTC 日志本身仍能读到变化的秒值。下面的 CP0 数值保留为旧 QEMU 历史数据，不是真机数据。

v0.11.1 仅更新性能诊断包：用 TCU5 的 32768 Hz RTC 输入计时，约 30.52 微秒分辨率，首次用 RTC 秒变化校验。仅借用已停止计数、没有 PWM 输出和待处理中断的 TCU5；不占用固件的 TCU0/1/2 与 PWM3/4，也不触碰 TCU6/7。全程屏蔽所借通道的中断，暂停/退出时恢复通道配置、计数、原中断掩码和时钟门控，恢复时重新借用而不重新做秒级校准。借用失败会明确记录 `TCU5_busy`，不生成伪造耗时。v0.11.1 方案在第二次真机测试失败，当前由 v0.11.2 修正。

16 位计数器约 2 秒回绕，运行中扩展到 32 位。若帧边界 RTC 检查发现可能超过一次回绕的长停顿，则记录 `fault=2` 并拒绝该次计时。暂停菜单的长时间停留不会计入，因为进入菜单之前已释放计时器。细分耗时分辨率为约 31 微秒，不能作为单条指令级测量。

## 本次修复

原来暂停会关闭声音设备、销毁 PCM 描述符，继续时重新初始化设备，并逐条打开、追加、关闭诊断日志。现在取消播放队列、清空音频环形缓冲，保留已初始化的设备和描述符；继续时调用开始播放并重新预缓冲。关闭声音、换 ROM 和退出仍释放设备；恢复失败则走重新打开设备的回退路径。

未变化的配置不再额外写日志，恢复时清理输入不再写两条日志。核心、ROM 分页缓存和 JIT 缓存不会因普通暂停而重新加载。读即时存档仍按核心要求刷新 JIT。

在完整 H1 V1.41 固件、同一个 AUDIO.gba 测试 ROM、同一私有 NAND 配置下，对普通包测三次继续游戏。延迟从触摸松开请求到游戏画面再次出现，包含本地 HTTP 和帧抓取开销：

| 项目 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 第一次恢复 | 437 ms | 78 ms |
| 第二次恢复 | 422 ms | 63 ms |
| 第三次恢复 | 422 ms | 62 ms |
| 恢复后逻辑帧率 | 未单独计数 | 三次均约 59.76 帧／秒 |

普通包恢复后录制 8.004 秒、32 kHz AIC 音频，512242 个声道样本全部非零；该持续音测试中没有静音断点。运行日志为 2185 个音频批次、4 次环形队列提交，丢弃、失败、环形欠载均为 0，显示错误 0，正常退出。

复用设备后，暂停期间 AIC DMA 可能继续输出静音，而游戏核心停止推进。三次暂停录音全部为 0，内存中的逻辑帧计数保持不变。退出时关闭声音设备和释放描述符。MIPS 自动检查还确认三次暂停／恢复仅初始化一次描述符、打开一次设备、最终关闭一次。

## 运行耗时

完整固件运行现有 16 MiB 绿宝石 ROM，默认保持比例、跳 1 帧、声音开启。JIT 日志确认 `enabled=1`，缓存 2490368 字节。计时使用只读 CP0 Count，经独立硬件 RTC 秒寄存器校准约 168 MHz；这里表示 QEMU 虚拟经过时间，包含中断及系统调度时间，不是执行的 MIPS 指令数。

每项按逻辑帧平均；占比的分母为核心运行时间，排除了限速等待、循环管理和电池存档检查。各层独占计时，子调用不会重复计入父调用：

| 工作 | 暂停前 ms／帧 | 继续后 ms／帧 | 暂停前计算占比 |
| --- | ---: | ---: | ---: |
| CPU／JIT 执行、事件及未细分核心工作 | 1.082 | 0.975 | 53.8% |
| GBA PPU 扫描线渲染 | 0.476 | 0.473 | 23.6% |
| 缩放、颜色转换、写 LCD framebuffer | 0.315 | 0.263 | 15.7% |
| 核心音频生成 | 0.024 | 0.024 | 1.2% |
| PCM 重采样及环形缓冲处理 | 0.016 | 0.015 | 0.8% |
| ROM 文件读取／定位 | 0.088 | 0.016 | 4.4% |
| JIT 缓存同步 | 0.009 | 0.001 | 0.4% |
| 核心输入轮询 | 0.001 | 0.001 | 0.1% |
| 核心运行总计 | 2.011 | 1.769 | 100% |

暂停前记录 1177 个逻辑帧、588 个实际输出画面；恢复后 1150 个逻辑帧、574 个输出画面，均约 60 个逻辑帧／秒。场景在动画中继续变化，表中前后差异不能当作同场景加速倍率。采样本身也有开销。

暂停前最慢核心帧 38.85 ms，5 帧超过 16.743 ms；继续后最慢 18.03 ms，1 帧超时。说明平均耗时小不代表每帧都稳定。本次未发现暂停后计算时间持续增长；音频环形欠载、丢弃和失败为 0。

限速等待每帧平均 14.66～14.88 ms，包含等待循环中的按键轮询。这不是核心计算瓶颈。更值得注意的是节奏：1177 帧中，613 个循环超过 25 ms，292 个循环不足 2 ms；恢复后的 1150 帧中也有 610 个超过 25 ms。模拟器 AIC 每次 DMA 处理 1000 个 32 kHz 样本，约 31.25 ms，软件队列游标随批次推进。现有按队列占用量限速容易让相邻逻辑帧集中运行，再等待下个批次。这能解释平均帧率正常时仍有不均匀的流畅感；真机也需用分析包验证。

## 下一步优化顺序

1. 平滑帧调度：以可靠的高精度单调时间按约 16.743 ms 安排逻辑帧，PCM 队列用于控制缓冲上下界及小幅纠偏，避免每个 DMA 批次唤醒后集中推进两帧。不能直接改回音频中断下会丢计数的固件软件毫秒计时器。
2. 细分 CPU／JIT：当前 CPU 栏包含译码、执行和事件处理，尚不能证明译码缓存未命中是瓶颈。进一步测 ARM／Thumb 翻译、缓存清理和内存访问热点，再决定扩大缓存或优化生成代码。
3. PPU 和最终输出：两项合计约 39% 的计算时间。优先优化扫描线／精灵热点和常用缩放路径，比较原始大小与保持比例的真机耗时。最终输出已经直接写 framebuffer，重复换成另一套整屏复制接口不会消除 PPU 和转换成本。
4. 控制尖峰：单独追踪 ROM 页缓存未命中、存档写入及系统中断。2 MiB 页缓存是否需要扩大，应以具体游戏的未命中率和 H1 剩余内存决定。测试 ROM 首次电池存档写入约 129 ms，已有 128 ms 音频预缓冲接近其量级，不能只看平均耗时。

## framebuffer 路径

gpSP 先在自己的 240×160 RGB565 缓冲里渲染 GBA 画面，前端通过 H1 `GUI+0x8F4` 取得当前 480×272、32 位 LCD framebuffer，再缩放、转换并直接写入。游戏阶段没有另外调用整屏 blit／present 来复制一遍；加载条和暂停菜单使用独立 RGB565 绘图缓冲。

## 在真机取日志

安装 `dist/H1GBA-profile.bda`，确保 `A:\GBA\` 可写，选择实际卡顿的 ROM，正常玩 15～30 秒，打开暂停菜单，继续，再正常玩一段并退出。复制 `A:\GBA\h1gba.log` 后再启动应用，因为每次启动会覆盖日志。

分析包在内存记录，每 300 个逻辑帧形成一个窗口，最多保留最近 12 个窗口；暂停或正常退出时才写 `PROFILE_*`。首次加载以 RTC 校准，继续时不重新校准。写统计会延长分析版进入菜单的等待，所以日常使用普通包。详细日志版 `H1GBA-debug.bda` 的日志 I/O 会影响运行，不用于计时。

```powershell
python tools/build.py --toolchain .tools/toolchain/bin --profile
python tools/analyze_profile.py h1gba.log --environment real-h1 --output profile.json
```

`core_mean_us`／`core_max_us` 为含前端回调的核心调用耗时；`PROFILE_COST` 为各项独占耗时。`core_p95_bin_ms=3` 表示 p95 落在 3～4 ms 桶，63 表示 63 ms 及以上。`over_16_743ms` 为核心调用超预算数量。计时器不可用或 scope 不平衡时不应使用该记录。
